# Ragged Fragment Reduction：布局修复与正确性验证

## 结论

CUDA 标量求和的默认布局推断能够为 `N=96/100/120/127` 选择合法候选，七种目标宽度均通过 GPU 数值验证。
修复保留显式源布局约束、replication 一致性检查、非 2 次幂归约和 warp 对齐的安全拒绝行为。

候选分组采用能够整除宽度的最大适用 2 次幂，避免使用现有复制循环无法正确处理的不完整尾部分组。
`N=127` 使用单 lane、全线程复制回退，属于正确性兼容方案，不能视为性能优化。

## 错误机制

原始布局将 `N=96` 的输入分配给 96 个线程，却将输出标量配置为 128 份复制。
`ComputeReducerLayout` 从输入得到的归约结果 replication 为 96，无法满足目标的 128 份 ownership。

`ProveFragmentContains` 对线程表达式为 `_rep` 的复制布局存在直接成功条件，不能单独保证满足归约 lowering 的全部约束。
原始程序能够通过 `LayoutInference`，在 `LowerTileOp` 的 `ReduceLowerer` 中被拒绝。
关键条件为 `dst replication <= reduced replication`。

将目标 replication 缩小到 96 也不足以解决问题，因为 XOR-butterfly AllReduce 要求逻辑线程宽度为正的 2 次幂。
修复需要合法的线程布局，不能仅删除或放宽检查。

## 合法布局对照

显式 32-lane 分组让 `N=96` 通过 arange、全 1、固定随机输入和正负抵消输入。
每组完整处理 96 个元素，每个 lane 持有 3 个值，4 个分组分别完成相同的归约。

32-lane 分组对 `N=100/120/127` 未能通过复制循环的布局验证，推断出的局部索引发生折回。
64-lane 候选同样未通过相应验证，因此没有将这些不完整分组用于自动候选。

能够整除宽度的分组均通过完整数值对照：

| N | 分组宽度 | 输入复制数 | 每线程逻辑 slot | 标量结果复制数 |
| --- | --- | --- | --- | --- |
| 96 | 32 | 4 | 3 | 128 |
| 100 | 4 | 32 | 25 | 128 |
| 120 | 8 | 16 | 15 | 128 |
| 127 | 1 | 128 | 127 | 128 |

分组宽度记为 `g`，源布局为：

```text
thread = rep * g + j % g
slot = j // g
replication = 128 / g
```

`g` 为正的 2 次幂，且同时整除宽度和线程数。
因此每组覆盖全部有效元素，每个线程恰好持有 `N / g` 个值，不存在需要读取的未初始化尾部 slot。
每组的线程内求和与组内 AllReduce 共同完成完整逻辑归约，输出的 128 份复制保持可用。
`g=1` 时只执行线程内求和，不需要跨线程 AllReduce。

## 编译器修改

### 推断与 lowering 的一致性

`ReduceOpNode::InferLayout` 将 replication 条件纳入候选检查，使用已有 `LayoutConflictException` 通道丢弃不兼容方案。
仅增加该条件时，`N=96` 仍因候选不足而编译失败；提前拒绝本身不构成完整修复。

公共 `ProveFragmentContains` 与底层 AllReduce 算法保持不变，lowering 的关键安全检查保留。

### 受限合法候选

`MakeRaggedSumLayout` 为自由推断提供经过数值验证的整除分组布局，候选仍由既有求解器传播并检查与其他使用者的兼容性。
已存在的源布局不会被替换，显式标注的非法布局仍被拒绝。

候选适用范围为：

- CUDA，float32，清零型 `reduce_sum`，非 batch、非流水场景。
- 输入和输出均为 Fragment，形状分别为静态 `(1, N)` 与 `(1,)`，归约维度为 1。
- 完整输入与输出区域，128 个线程，线程范围从 0 开始。
- `32 < N < 128`，且 `128` 不能被 `N` 整除。
- 源布局尚未确定，也没有显式源布局约束。

候选从 32 开始向下寻找能够整除 `N` 的 2 次幂分组。
`N=64/128/256` 不进入回退路径，保留原有布局。
逐元素循环的默认布局规则没有修改。

## 数值验证与回归

正式回归覆盖七种宽度，每种宽度使用 arange、全 1、固定随机输入和正负抵消输入。
输出在执行前填充 NaN，GPU 同步后与 PyTorch 高精度累加再转换为 float32 的参考结果比较。
前三类输入使用 `rtol=0, atol=1e-4`；抵消输入的绝对容差根据机器精度与输入绝对值之和确定，避免归约顺序造成误判。

| 验证项目 | 结果 |
| --- | --- |
| 新增回归在原始编译器上的结果 | 4 失败、4 通过 |
| 七种默认形状及显式源约束回归 | 8 通过 |
| 完整归约测试文件 | 114 通过、1 跳过 |
| 相关布局推断回归 | 5 通过 |
| Compute Sanitizer 内存检查 | 7 通过，0 个错误 |

非 2 次幂 AllReduce 宽度、warp 未对齐和非连续参与 warp 的拒绝测试保持通过。
部分线程 barrier、偏移线程范围、完整分组和 batch 归约路径均包含在归约回归中。
显式源布局的负向测试确保编译器不会为获得可执行结果而偷偷覆盖用户约束。

原始最小程序也通过 GPU 数值复测。
Issue #2398 的 `N=129/229/257` 仍在布局推断失败，其修复不属于归约补丁范围。

## 限制与性能风险

该方案优先保证原先无法编译的静态标量求和能够正确执行，不提供性能提升保证。
`N=100/120` 需要较多输入复制和局部 slot；`N=127` 的单 lane 回退具有 128 份输入复制和每线程 127 个逻辑 slot，代价尤其明显。
逻辑 slot 数来自生成代码的局部数组，不能直接等同于最终物理寄存器用量。

性能评估需要分别检查编译器优化后的访存、寄存器与执行时间，再判断是否需要更高效且经过证明的尾部布局。
任意形状、其他线程数、其他 dtype、其他后端、max/min 与流水场景未获得新的支持保证。
完整跨后端测试和更广泛应用算子的回归不包含在上述验证范围内。
