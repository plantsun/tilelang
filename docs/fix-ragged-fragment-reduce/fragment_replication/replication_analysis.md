# Fragment Replication 分析

## 基线与复现

实验使用固定的官方源码基线和 A100，源码标识保存在 `versions.toml`。Fragment 为 FP32，线程块包含 128 个线程；每个成功运行的算子都用递增值、全 1 和固定种子的随机输入对照参考结果。

| 逻辑宽度 N | `T.copy` 往返 | `T.Parallel` 逐元素运算 | `T.reduce_sum` |
| --- | --- | --- | --- |
| 64、128、256 | 通过 | 通过 | 通过 |
| 96、100、120、127 | 通过 | 通过 | 布局不一致，编译失败 |
| 192、229、257 | 无可用布局 | 无可用布局 | 循环布局非单射 |

大于线程数的非整除宽度在纯 Copy 中也会失败，说明该组样例不依赖 Reduction；它与已有 Elementwise 问题是否具有完全相同的根因仍需单独证明。逐项结果见 [隐式布局数据](results/implicit/execution.json)。

## 逻辑到物理的映射

对 N=96 的默认归约，输入 Copy 所采用的候选将第 `j` 个元素放到线程 `j`，每个元素一份，线程覆盖 `[0, 96)`。单独的 Copy 和 Elementwise 可以使用这一布局，因此不能只凭未使用全部线程就把源布局判定为普遍非法。

输出标量布局的复制范围为 `[0, 128)`。将输入布局沿归约维度投影后，归约结果的复制范围为 `[0, 96)`：两者组合起来不能满足 128 个目标线程都持有结果的要求。

独立候选采用 `thread = 32 * replica + j % 32`、`slot = j // 32`，每个 Warp 持有一份逻辑数据。N=96 时复制数为 4，每个线程持有 3 个有效元素。该布局的正逆映射逐项吻合；显式布局的 Copy、Elementwise 和 Reduce 均通过数值检查。全 1 输入也通过，结果没有把四份副本重复相加。

| N | 每线程物理槽位 | 每个 Warp 的填充槽位 | 严格逆映射 | 带保护逆映射的有效槽位往返 |
| --- | --- | --- | --- | --- |
| 96 | 3 | 0 | 通过 | 384 / 384 |
| 100 | 4 | 28 | 不通过 | 400 / 400 |
| 120 | 4 | 8 | 不通过 | 480 / 480 |
| 127 | 4 | 1 | 不通过 | 508 / 508 |

表中的槽位是布局模型中的数量，不是实测寄存器数。严格逆映射要求静态映射双射；不规则宽度存在未使用的物理槽位，因此不满足这一要求。`InverseWithLevel(true)` 使用允许填充保护的路径，逐项枚举的有效槽位全部往返，剩余槽位必须由调用方保护。这个有限范围的枚举不等于对任意形状的证明。

完整映射和检查结果见 [映射摘要](results/mapping/mappings.json)、[逐项映射](results/mapping/mappings.csv) 和 [包含性与保护逆映射探针](results/contains.json)。

## 首个不兼容的推断结果

N=96 的通用循环分区计算 `128 / 96 = 1`，生成线程范围为 96、复制数为 1 的输入候选。简单向上取整会得到 192 个线程位置，超过线程块范围，不能直接替换该除法。

`LayoutInference` 将输入布局与 128 份目标标量布局同时保留。`ReduceOpNode::InferLayout` 根据输入调用 `ComputeReducerLayout`，得到 96 份结果，并用 `ProveFragmentContains` 检查目标布局是否由归约结果覆盖。实际包含性探针直接调用该函数：

| 小集合（目标） | 大集合（归约结果） | 枚举线程集合 | 函数返回 |
| --- | --- | --- | --- |
| 128 个线程 | 96 个线程 | 不包含 | 包含 |
| 96 个线程 | 128 个线程 | 包含 | 包含 |
| 96 个线程 | 96 个线程 | 包含 | 包含 |

实现把 `forward_thread = _rep` 视为完全复制，并直接返回兼容；该快速路径没有验证两侧线程范围。N=96 样例因此在布局推断阶段保留了不兼容的输入和目标组合，随后 `LowerTileOp` 中现有的归约安全检查发现目标复制数 128 大于归约结果复制数 96 并停止编译。

独立探针还构造了线程范围相同、物理槽位分别为 0 和 1 的完全复制布局：启用物理槽位比较时，函数仍返回兼容。这表明该快速路径也绕过了调用方请求的槽位比较；该反例与 N=96 的归约失败需要分别修正和验证。

直接探针证明了这个包含性判断的误报；它本身不能证明修正判断后编译器就能找到新的合法候选。通用候选生成、传播和填充保护仍需要配套设计。

## 复制与归约不变量

1. 每个合法逻辑元素都必须有至少一个有效物理位置，线程和槽位不得越界。
2. 线程持有的物理槽位结构必须符合消费者要求；填充槽位需要显式边界保护和正确初始化。
3. 正映射和用于执行的逆映射应在所有有效坐标上往返一致；复制坐标和逻辑坐标不能互相混淆。
4. 归约中只累计独立逻辑项；等价副本不能重复计入，复制输出写回时应选择正确的所有者。
5. 布局包含性需要验证实际线程集合和必要的物理槽位约束，不能仅依据映射表达式的形状。

## 候选布局与执行边界

| 布局 / 操作 | N=96 | N=100、120、127 |
| --- | --- | --- |
| 显式 Warp 复制，直接 `T.copy` | Copy、Elementwise、Reduce 均通过 | 循环布局出现物理位置冲突，编译失败 |
| 扩大 Fragment 到完整 Warp 槽位后复制切片 | 三类操作均通过 | 复制切片的循环布局仍冲突 |
| 完整填充 Fragment，使用边界保护循环读写 | 三类操作均通过 | 三类操作均通过 |

对于 N=100，复制切片时推导出的循环槽位表达式将逻辑位置 0 与 96 映射到同一物理位置；这与原始候选的 `j // 32` 不同。仅扩大 Fragment 的形状并不能保证局部复制的循环布局传播正确。

受保护的完整填充循环先将无效位置置零，归约覆盖填充后的 Fragment。生成代码在每个 Warp 内归约，并由一个线程写回标量；Copy 写回也限制为一个副本。N=100 的受保护 Copy 和 Reduce 分别通过 memcheck 与 racecheck，均为零错误或零 hazard。检查范围仅覆盖这些样例，不代表完整的并发正确性证明。[执行数据](results/explicit/execution.json)、[保护循环数据](results/guard/execution.json) 与 [Sanitizer 摘要](results/sanitizer.json) 分别保留。

## 历史方案的边界

历史方案在 Reduction 中按宽度选择可整除的线程分组，缓解了特定 FP32 求和的编译失败。维护者关闭 [PR #3566](https://github.com/tile-ai/tilelang/pull/3566)，指出该方案不符合 Fragment 和 Reduction 的预期复制语义。已有实验数据仍可用于理解该受限原型，不应视为上游接受的通用修复。

## 建议的编译器改进

1. 收紧完全复制的包含性快速路径：证明实际线程集合覆盖，并在要求比较物理槽位时保留相应检查。为 128 对 96、96 对 128、相等范围及不同槽位构造反例与控制用例。
2. 在通用布局候选生成和选择中研究合法的复制布局，先覆盖能由完整 Warp 均匀分配的形状；测试应同时覆盖 Copy、Elementwise 与 Reduce，而非只为某个 Reduction 增加特例。
3. 针对非完整 Warp，研究受保护的逆映射与无效槽位初始化，并检查切片循环布局传播为何产生重复位置。保护路径使用宽松映射检查，必须额外证明有效域的单射与边界条件。
4. 在不削弱现有归约安全检查的前提下，验证复制输出的所有权、不同归约类型和累积模式；结合实际工作负载与动态计数评估性能。

这些是依据现有证据提出的设计方向，尚未作为编译器补丁实现。

## 需要上游确认的问题

- Fragment 是否要求所有线程持有同样数量的有效逻辑元素，还是允许物理槽位均匀、部分槽位由保护条件屏蔽？
- 布局包含性应如何比较不同线程范围、复制坐标和物理槽位？受 Warp 特化影响的线程偏移应采用什么约定？
- 不规则 Fragment 的填充保护应由 Layout、循环分区还是布局传播维护？切片和 Reduction 如何共享同一有效域信息？
- Warp 级复制候选应如何与布局成本模型、其他目标后端以及显式布局约束协同？
