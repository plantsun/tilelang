# Fragment 编译与执行开销

## 方法

实验使用 A100、FP32、128 线程。每个组合在独立进程中关闭编译缓存，执行三次编译；编译耗时为编译接口的墙钟时间，包含设备代码编译和模块装载，不包含 Python 进程启动。成功编译后先对递增值、全 1、随机输入做数值验证，再使用 CUDA Graph 和 GPU Event 计时；每次图重放包含 100 次内核运行，每个编译样本记录 10 次计时。表中为三次编译中位数，以及三组图计时中位数的中位数。

基线的 N=96、100、120、127 隐式布局均无法编译；相应的运行时对照采用经过正确性检查的显式 Warp 布局或 Padding + Guard。N=128、256 两侧均使用隐式布局。不同实现之间的延迟对照不是从编译失败计算出来的加速比。

| N | 基线运行时对照 | 基线编译 ms | 修复后隐式编译 ms | 基线执行 μs | 修复后隐式执行 μs |
| --- | --- | ---: | ---: | ---: | ---: |
| 96 | 显式 Warp | 1357.3 | 1371.6 | 1.505 | 1.500 |
| 100 | Padding + Guard | 1394.8 | 1342.1 | 1.500 | 1.495 |
| 120 | Padding + Guard | 1369.0 | 1321.6 | 1.475 | 1.500 |
| 127 | Padding + Guard | 1418.2 | 1407.3 | 1.495 | 1.475 |
| 128 | 隐式 | 1265.5 | 1245.6 | 1.567 | 1.572 |
| 256 | 隐式 | 1363.8 | 1285.5 | 1.562 | 1.546 |

测量是小型内核微基准；基线和最终修复版本分别采样，次序未随机化。采样次数有限，编译时间受设备编译器、文件缓存和共享主机负载影响。差异不能直接解释为稳定的性能收益或回归，也不能说明端到端模型性能。

## 所有权证明的编译期开销

隔离调用复制压缩接口，每种形状预热两次并测量十次；表中是单次调用的中位数。这里仅测量构造好的 Fragment 的压缩，不包含 GPU 执行，也不能代表整模型编译时间。

| N | 基线 ms | 修复后 ms | 基线所有权等价 | 修复后所有权等价 |
| --- | ---: | ---: | --- | --- |
| 96 | 0.039 | 3.173 | 是 | 是 |
| 100 | 0.029 | 1.846 | 否 | 是 |
| 120 | 0.029 | 1.820 | 否 | 是 |
| 127 | 0.029 | 2.037 | 否 | 是 |
| 128 | 0.038 | 3.132 | 是 | 是 |
| 256 | 0.038 | 3.022 | 是 | 是 |

对这些探针，证明与枚举增加约 1.8–3.1 ms；正常形状也受到影响。编译接口的单内核结果中未观察到可据此判定的稳定大幅回归，但样本不足以保证复杂模型无明显影响。需要在真实工作负载上测量调用次数与整体编译延迟，并研究更便宜的符号证明或缓存。超出验证预算且无法符号证明时保留原布局，可能带来保守拒绝。
